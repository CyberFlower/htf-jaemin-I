# Use Case · 기능 요구사항 공통 템플릿

> 상태: 제안. 앱별 문서를 작성할 때 복사해 쓰는 양식입니다. 기존 요구사항과 팀의 결정을 자동으로 변경하지 않습니다.

## 1. 무엇을 어디에 쓰는가

| 문서 | 답하는 질문 | 양식 |
|---|---|---|
| `GOAL.md` | 누구의 어떤 문제를 왜 해결하는가? | 프로젝트의 기존 문서 |
| `USE_CASES.md` | 사용자가 어떤 상황에서 시스템과 상호작용해 목표를 이루는가? | [Use Case](use-cases.md) |
| `REQUIREMENTS.md` | 시스템이 어떤 조건에서 무엇을 해야 하는가? | [기능 요구사항(FR)](functional-requirements.md) |
| `OPEN_QUESTIONS.md` | 아직 확인하거나 결정하지 못한 것은 무엇인가? | 프로젝트의 기존 질문 표 |
| `DECISIONS.md` | 무엇을 합의했고, 왜 그렇게 정했는가? | 프로젝트의 기존 결정 양식 |

Use Case는 사용자 목표 하나를 달성하는 흐름을, FR은 독립적으로 검증할 시스템 동작을 적습니다. 사용자 이야기는 필요와 이유를 요약하며, 기본·대안·예외 흐름을 대신하지 않습니다. 비기능·공통 원칙은 기존 `REQUIREMENTS.md`의 해당 절에 둡니다.

## 2. 복사해서 시작하기

1. 프로젝트의 `GOAL.md`, `REQUIREMENTS.md`, `OPEN_QUESTIONS.md`, `DECISIONS.md`를 읽습니다.
2. [Use Case 양식](use-cases.md)을 `projects/<project>/USE_CASES.md`로 복사하고, 사용자 목표 하나를 작성합니다. 기존 프로젝트에는 필요한 시나리오부터 점진적으로 추가합니다.
3. 흐름에서 필요한 시스템 동작을 찾아 [FR 블록](functional-requirements.md)을 `REQUIREMENTS.md`의 기능 절에 추가하거나 기존 항목을 보강합니다.
4. Use Case의 흐름과 FR을 양쪽에서 연결합니다. FR의 수용 기준은 관찰 가능한 결과로 씁니다.
5. 확인하지 못한 정책·기술은 질문 ID로 연결하고, [리뷰 체크리스트](#6-리뷰-체크리스트)를 확인합니다.

[작성 예시](example.md)는 가상의 일반 앱으로 두 양식을 채운 예입니다. 제품 요구사항이나 합의된 결정이 아닙니다.

## 3. ID와 연결 규칙

`APP`은 프로젝트 코드 자리표시자입니다. 이 저장소에서는 다녀왔습니다에 `GRD`, 내 차로 짓는 도시에 `GAM`을 씁니다. 다른 앱에서는 해당 앱의 코드로 바꿉니다.

| 대상 | 공통 표기 | 이 저장소 예 |
|---|---|---|
| Goal | `APP-G1` | `GRD-G1`, `GAM-G1` |
| Use Case | `APP-UC-001` | `GRD-UC-001`, `GAM-UC-001` |
| 기능 요구사항(FR) | `APP-001` | 기존 `GRD-001`, `GAM-001` 유지 |
| 비기능·원칙 | `APP-N01` | 기존 `GRD-N01`, `GAM-N01` 유지 |
| 프로젝트 질문 | `APP-Q1` | `GRD-Q1`, `GAM-Q1` |
| 프로젝트 결정 | 파일 경로 + `D-001` | `projects/game/DECISIONS.md`의 `D-001` |
| 저장소 공통 결정 | ADR 파일 경로 | `docs/decisions/0001-repo-structure.md` |

- 기존 FR에 `FR-` 접두어를 새로 붙이거나 번호를 재할당하지 않습니다. 번호는 재사용하지 않습니다.
- Use Case의 기본 흐름은 `B1`, 대안 흐름은 `A1`, 예외 흐름은 `E1`부터 붙입니다. 다른 문서에서는 `APP-UC-001 / E1`처럼 Use Case ID와 함께 참조합니다.
- 한 Use Case에 여러 FR이 연결될 수 있고, 한 FR을 여러 Use Case가 공유할 수 있습니다. 흐름 전체를 FR 하나에 몰아넣거나, 화면·버튼마다 Use Case를 나누지 않습니다.
- Use Case의 연결 표에는 흐름과 FR ID를, FR의 `관련 UC`에는 Use Case ID와 흐름 번호를 적습니다. 둘 중 하나를 바꾸면 반대편 연결도 확인합니다.
- UC를 아직 작성하지 않은 기존 FR은 기존 ID와 내용을 유지합니다. 연결은 점진적으로 추가하며, `관련 UC: 미작성`을 확정된 연결처럼 취급하지 않습니다.

## 4. 기존 Decisions와 함께 쓰기

[AGENTS.md](../../../AGENTS.md)의 우선순위를 따릅니다. 사람이 확정한 결정과 Confirmed 요구사항을 기준으로 UC·FR을 작성합니다. UC가 기존 Goal이나 결정을 덮어쓰지 않습니다.

- **미결정:** 프로젝트의 `OPEN_QUESTIONS.md`에 질문을 적습니다. UC·FR의 `미결정`에서 파일과 질문 ID를 참조합니다. 제안 중인 답을 결정으로 쓰지 않습니다.
- **합의한 결정:** 기존 `DECISIONS.md`의 `D-###`, 제목·날짜와 `결정 / 이유 / 영향 / 합의` 필드를 그대로 씁니다. `영향`에 바뀌는 UC·FR ID와 문서를 함께 적을 수 있습니다.
- **결정의 범위:** 프로젝트 결정은 해당 `DECISIONS.md`에, 저장소 전체 결정은 기존 [ADR 체계](../../decisions/README.md)에 둡니다. UC 양식 도입으로 별도의 결정 파일이나 상태 체계를 만들지 않습니다.
- **참조:** 프로젝트마다 같은 `D-001`이 있을 수 있으므로 파일 경로와 ID를 함께 적습니다. 예: [game의 DECISIONS.md](../../../projects/game/DECISIONS.md)에 있는 `D-001`. 결정 내용은 UC·FR에 복사하지 않습니다.
- **변경:** Confirmed 요구사항이나 Goal은 기존 규칙대로 먼저 결정 이유를 기록합니다. UC·FR이 결정과 충돌하면 질문으로 남기고 변경을 제안합니다.
- **상태와 권한:** FR의 상태·우선순위·SDK 검증 태그는 [기존 가이드](../requirements-guide.md)를 그대로 따릅니다. UC 상태도 같은 Draft / Review / Confirmed / Deferred / Dropped를 사용합니다. 에이전트는 Draft·Review까지만 제안하며, 확정·보류·폐기는 사람이 합니다.

## 5. 앱별 조건 적용

공통 양식의 핵심은 사용자·상황·흐름·시스템 동작·수용 기준·근거입니다. 실행 환경에 해당하는 조건을 추가합니다.

| 조건 | 작성할 내용 |
|---|---|
| 이 저장소의 공모전 앱 | 모든 요구사항에 기존 심사 태그를 하나 이상 기입. 기존 P0/P1/P2 정의 유지 |
| 차량 앱 | 주행·정차 제약, 신호 오판 방지, 사용자 승인, SDK capability 부재 시 대체 동작 |
| 외부 서비스·기기 의존 | 권한 거부, 네트워크·API 실패 시 결과와 대체 동작, 근거와 검증 상태 |
| 개인정보·외부 전송·제어 | 동의·승인 시점, 취소 시 결과, 저장·공유 범위 |
| 다른 환경의 앱으로 복사 | 해당 프로젝트의 규칙에 맞게 심사·우선순위·검증 필드를 조정. 이 저장소 문서를 편집할 때는 기존 규칙 유지 |

적용되지 않는 조건은 `해당 없음`과 이유를 씁니다. 아직 모르는 조건은 `확인 필요`와 질문 ID를 적습니다. 둘을 혼용하지 않습니다.

## 6. 리뷰 체크리스트

- [ ] Use Case가 사용자 목표 하나와 시작·종료 조건을 설명한다
- [ ] 기본 흐름에서 사용자 행동과 시스템 응답이 구분된다
- [ ] 대안·예외에 분기 시점과 복귀 또는 종료 지점이 있다
- [ ] FR 하나가 독립적으로 검증할 동작을 설명한다
- [ ] 성공·실패·취소 중 해당하는 결과를 수용 기준으로 확인할 수 있다
- [ ] Goal → UC 흐름 → FR → 수용 기준의 연결이 맞는다
- [ ] 기존 FR·질문·결정 ID를 바꾸거나 재사용하지 않았다
- [ ] 관련 결정은 파일과 ID로 참조하고, 충돌·미결정은 질문으로 남겼다
- [ ] 근거 없는 API·수치·합의가 없고, 필요한 검증 태그와 대체 동작이 있다
- [ ] 이 저장소의 심사 태그, 차량 원칙, 사람의 확정 절차를 지킨다
