# 작성 예시: 목록 항목 이름 변경

> 가상의 목록 관리 앱 `APP`을 사용한 양식 예시입니다. 실제 앱의 요구사항·결정·검증 결과가 아닙니다. 제품 문서로 옮길 때는 근거와 Goal, 적용 규칙을 확인합니다.
> 아래 심사 태그와 우선순위도 양식 사용 예시이며, 이 기능의 공모전 적합성을 입증하지 않습니다.

## 예시 Goal

`APP-G1`: 사용자가 저장한 목록을 자신의 상황에 맞게 정리한다.

## 예시 Use Case

### APP-UC-001 목록 항목 이름 바꾸기

- 상태: Draft
- 목표: APP-G1 (위 예시 Goal)
- 주 행위자: 목록을 관리하는 사용자
- 보조 행위자: 없음
- 사용자 목표: 목록의 항목을 나중에도 알아볼 수 있도록 이름을 고친다.
- 범위: 앱 내부의 항목 이름 변경. 계정·외부 공유는 다루지 않는다.
- 트리거: 사용자가 기존 항목의 이름 변경을 시작한다.
- 사전 조건: 이름을 변경할 항목이 앱 내부 저장소에 존재한다.
- 성공 후 조건: 변경한 이름이 저장되고 목록에 표시된다.
- 실패·취소 후 조건: 기존 이름은 유지된다. 저장 실패 시 수정 중인 입력을 유지하고, 취소하면 수정 중인 입력을 버린다.
- 관련 결정: 없음 (작성 예시)
- 미결정: 없음 (이 예시에서 정의한 범위 안)
- 출처: 공통 템플릿을 설명하기 위한 가상 시나리오

#### 기본 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|---|---|---|
| B1 | 기존 항목의 이름 변경을 시작한다 | 현재 이름을 수정할 수 있게 제공한다 |
| B2 | 새 이름을 입력하고 저장한다 | APP-001의 입력 규칙으로 검사하고 새 이름을 저장한다 |
| B3 | — | 저장 완료를 알리고 목록에 새 이름을 표시한다 |

#### 대안 흐름

없음. 이 예시는 한 가지 입력·저장 경로만 다룬다.

#### 예외·취소 흐름

| ID | 분기 단계·조건 | 행동과 시스템 응답 | 복귀·종료 |
|---|---|---|---|
| E1 | B2에서 입력 규칙에 맞지 않는다 | 시스템이 이유를 알리고 기존 이름과 수정 중인 입력을 유지한다 | B2로 복귀 |
| E2 | B2에서 저장에 실패한다 | 시스템이 실패를 알리고 기존 이름과 수정 중인 입력을 유지한다 | B2로 복귀, 재시도 가능 |
| E3 | B1~B2에서 사용자가 저장 요청 전에 취소한다 | 시스템이 수정 중인 입력을 버리고 기존 이름을 유지한다 | 취소 종료 |

#### 실행 환경·제약

- 앱 내부 로컬 저장만 사용하는 예시이며, 네트워크·외부 서비스·차량 신호·외부 전송·제어 승인은 해당하지 않는다.
- 저장에 실패하면 E2로 진행한다. 실제 앱의 차량·권한 제약은 해당 앱의 원칙을 추가해 작성한다.

#### 흐름과 요구사항 연결

| 흐름 | FR ID | 연결 이유 |
|---|---|---|
| B1~B3, E1~E3 | APP-001 | 이름 변경의 성공·실패·취소 동작 |

## 예시 FR

### APP-001 목록 항목 이름 변경
- 상태: Draft · 우선순위: P1 · 심사: [사업] · 목표: APP-G1
- 이야기: 목록 사용자로서 저장된 항목의 이름이 알아보기 어려울 때 이름을 고치고 싶다. 그래야 목록을 내 상황에 맞게 정리한다.
- 관련 UC: 이 문서의 APP-UC-001 / B1~B3, E1~E3
- 동작: 시스템은 사용자가 입력한 이름의 앞뒤 공백을 제거하고, 결과가 빈 문자열이 아니면 기존 항목의 이름을 변경해 저장한다.
- 수용 기준:
  - AC1 (B1~B3): 저장된 항목에 새 이름을 입력해 저장하면, 앞뒤 공백을 제거한 이름이 목록에 표시되고 앱을 다시 열어도 유지된다.
  - AC2 (E1): 빈 입력 또는 공백만 있는 입력으로 저장하면, 입력 오류를 알리고 기존 이름과 수정 중인 입력을 유지한다.
  - AC3 (E2): 저장이 실패하면 성공을 표시하지 않고 기존 이름과 수정 중인 입력을 유지한다. 사용자는 다시 저장을 시도할 수 있다.
  - AC4 (E3): 저장 요청 전에 취소하면 수정 중인 입력을 버리고 기존 이름을 유지한다.
- 의존: 앱 내부 로컬 저장. 외부 서비스·SDK 의존은 없음 (가상 예시의 범위)
- 대체 동작: 저장 실패 시 오류를 알리고 수정 중인 입력을 유지해 재시도할 수 있게 한다.
- 데모: 예정 — 정상 입력, 공백 입력, 저장 실패를 주입한 경우, 저장 전 취소를 각각 실행하고 수용 기준의 결과를 확인한다. 실제 검증은 수행하지 않았다.
- 출처: 이 문서의 가상 시나리오
- 관련 결정: 없음 (작성 예시)
- 미결정: 없음 (이 예시에서 정의한 범위 안)

정책 변경을 논의한다면 실제 프로젝트의 `OPEN_QUESTIONS.md`에 질문을 만들고, 합의 후 기존 `DECISIONS.md` 형식으로 결정·이유·영향·합의를 기록합니다. 이 예시만으로 합의된 결정을 만들지 않습니다.
