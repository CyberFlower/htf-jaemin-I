# 기능 요구사항(FR) 블록

아래 블록을 `REQUIREMENTS.md`의 기능 절에 복사합니다. 기존 FR을 보강할 때는 기존 ID를 유지합니다. `APP`은 프로젝트 코드로 바꿉니다.

한 FR은 독립적으로 검증할 시스템 동작 하나를 설명합니다. 연결 규칙과 Decisions와의 관계는 [공통 안내](README.md), 상태·우선순위·검증 태그는 [요구사항 가이드](../requirements-guide.md)를 따릅니다.

```markdown
### APP-001 <시스템이 제공하는 기능의 짧은 제목>
- 상태: Draft · 우선순위: P1 · 심사: <이 저장소에서는 기존 태그 하나 이상> · 목표: <APP-G1>
- 이야기: <누구>로서 <어떤 상황>에서 <무엇>을 하고 싶다. 그래야 <이유>.
- 관련 UC: <USE_CASES.md의 APP-UC-001 / B2, E1 등. 기존 UC가 없으면 미작성>
- 동작: <시스템은 어떤 조건·입력을 받으면 무엇을 수행하고 어떤 결과·상태를 보장한다>
- 수용 기준:
  - AC1 (성공): <주어진 상태에서 특정 행동을 하면 관찰할 수 있는 결과>
  - AC2 (실패·경계): <잘못된 입력·권한 거부·외부 실패 등 해당하는 조건에서 보장할 결과>
  - AC3 (취소·오판 방지): <해당하는 경우 실행하지 않을 작업과 보존할 상태>
- 의존: <SDK 도메인/API (퍼미션) — 기존 검증 태그>, <외부 서비스와 근거>. 없으면 없음
- 대체 동작: <의존 미지원·실패 시 결과. 해당하지 않으면 이유>
- 데모: <수용 기준을 확인할 시연·검증 방법. 예정과 검증 완료를 구분>
- 출처: <기획안 절, Issue, 조사 근거 등>
- 관련 결정: <DECISIONS.md 또는 ADR의 파일 경로와 ID. 없으면 없음>
- 미결정: <OPEN_QUESTIONS.md의 파일 경로와 질문 ID. 없으면 없음>
- 메모: <선택. 수치·정책의 근거 또는 적용 범위>
```

- 수용 기준은 필요한 만큼 추가합니다. 해당하지 않는 실패·취소 항목은 이유와 함께 표시합니다.
- UC에는 사용자와 시스템이 주고받는 흐름을, FR에는 검증할 동작·정책을 씁니다. 상세 정책은 FR에서 관리하고 UC에서는 ID로 참조합니다.
- 차량 신호를 쓰면 오판 케이스, capability 부재 시 대체 동작을 적습니다. 외부 전송·차량 제어는 승인 시점과 승인하지 않았을 때의 결과를 명시합니다.
- 모르는 내용을 `없음`으로 처리하지 않습니다. `확인 필요`로 적고 질문 ID를 연결합니다.
- 기존 `이야기 / 수용 기준 / 의존 / 데모 / 출처 / 메모` 필드는 유지합니다. 비기능·원칙의 기존 양식과 ID는 바꾸지 않습니다.
