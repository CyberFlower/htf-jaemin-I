| 구분 | 필수 여부 | 내용 |

## 3. 접수 방법

- 이메일: `appdevchallenge@hyundai-partners.com`
- 제목: `[차량용 앱 개발 공모전] 팀명_대표자명`
- 팀원 전원을 참조(CC)에 넣습니다. CC만으로 동의를 대신할 수 없으므로 각자 서명해야 합니다. CC 주소는 팀원끼리 서로 보입니다.
- 본문에 **저장소 주소와 최종 커밋 hash**를 적습니다.
- 수정 제출: 처음 보낸 주소에서 다시 보냅니다. 제목 앞에 `[수정제출]`을 붙이고, 전체 자료와 서명한 동의서를 모두 다시 첨부하고, 전원을 CC에 넣습니다. 마감 전 마지막 제출본을 심사합니다.

## 4. 접수양식 구성

| 장 | 내용 | 작성 위치 |
|---|---|---|
| 01 참가신청서 | 참가 단위, 부문(대학(원)생 / 일반), 팀명, 앱명, 대표자 정보, 구성원 표(성명·소속·연락처·이메일·역할) | **저장소 밖에서** 작성 |
| 02 앱 프로젝트 소개 / 심사 자료 | 1. 한 줄 소개 · 2. 기획 배경 · 3. 주요 기능 및 차량 특화 요소 · 4. 주요 사용 시나리오 · 5. 개발 계획(SDK/API) · 6. 기대효과 및 발전 가능성 · 7. 참고자료 · 8. 숏폼 링크 | `projects/<p>/PROPOSAL.md` 원고 |
| 03·04 동의서 | 전원 개별 서명 | 저장소 밖에서 작성 |

양식 02를 쓸 때 알아 둘 것 (접수양식 DOCX 본문, 2026-11-14 확인):

- 맨 위에 `앱명 / 프로젝트명`을 적습니다. 접수번호는 운영사가 적으므로 비워 둡니다.
- 분량 제한이 없습니다. 여러 줄 항목의 작성란은 4줄 정도이고, 내용이 길면 늘어납니다. 필요하면 별지를 추가할 수 있습니다.
- 7번 참고자료는 파일 또는 링크로 냅니다. 8번 숏폼은 게시한 세로 영상의 링크를 적습니다.
- 메일 제목의 팀명 자리에는 개인 참가일 때 성명을 씁니다: `[차량용 앱 개발 공모전] 팀명(개인은 성명)_대표자명`
- 항목별 안내 문구 원문은 [접수양식 원고 양식](../process/templates/proposal.md)에 있습니다. 세 제출물(목업 틀, 코어 시나리오 가이드, 원고)을 함께 채우는 규칙은 [submission-package.md](../process/submission-package.md)에 있습니다.

양식 02와 공유 자료에 관한 주의 문구(원문):

> 대표자·구성원의 성명, 연락처, 이메일, 소속은 기재하지 않습니다.
> 공유 링크와 첨부자료에도 개인정보·계정정보·개발자 실명이 노출되지 않도록 확인하세요.

## 5. GitHub 저장소 규칙

- 공개·비공개 모두 제출할 수 있고, 심사용 계정을 Collaborator로 초대하지 않아도 됩니다.
- 비공개면 **2026-11-16까지 공개로 전환하고 2026-11-23까지 유지**해야 합니다. 전환하지 않으면 산출물 가산점이 반영되지 않습니다.
- 심사 기준 커밋: 제출 안내는 메일에 적은 커밋 hash를 기준으로 심사한다고 하고, FAQ는 11/16 기준 최종 커밋으로 심사한다고 합니다. 두 기준이 어긋나지 않게 하려면 **제출 후 11/23까지 `main`에 push하지 않습니다.** 이후 작업은 다른 브랜치에서 합니다.
- APK: `apk/팀명_앱이름_release.apk`. 실행할 수 있는 release 빌드여야 합니다. 용량이 크면 GitHub Releases에 올리고 Release 주소를 제출합니다.
- 저장소를 공개하기 어려우면 소스와 APK를 압축한 파일의 내려받기 주소를 마감 전에 메일로 보냅니다.

### README.md 필수 항목 (공식)

1. 앱 이름 및 한 줄 소개
2. 실행 방법
3. 테스트 환경 및 필요한 설정
4. 개발에 사용한 Pleos Connect 에뮬레이터 버전과 화면 규격
5. APK 파일 위치 또는 GitHub Release 링크

루트 [README.md](../../README.md)의 "제출 정보" 절에 채웁니다.

### 두 출품작을 한 저장소로 낼 때의 안내 (팀 결정, [open-questions.md](../open-questions.md) Q2)

grandma와 game은 각각 접수하지만 저장소는 하나입니다. 심사자가 앱을 헷갈리지 않도록 아래처럼 안내합니다.

- README "제출 정보"를 앱별 절(`다녀왔습니다 (GRD)`, `내 차로 짓는 도시 (GAM)`)로 나누고, 절마다 위 5개 항목을 따로 채웁니다.
- 각 접수 메일의 양식 02 7번(참고자료)에 저장소 주소와 함께 **해당 앱의 README 절 링크**, 해당 앱의 APK 경로를 적습니다. 다른 앱도 같은 저장소에 있다는 것을 한 줄로 밝힙니다.
- APK는 `apk/팀명_앱이름_release.apk` 규칙대로 앱 이름으로 구분합니다.
- 커밋 hash는 두 메일에 같은 값을 적습니다.

## 6. 공개 전 개인정보 점검

- [ ] 문서·코드에 실명, 연락처, 이메일, 계정 ID가 없습니다. 예: `git grep -nE "[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,}"`로 이메일 주소를 찾습니다.
- [ ] 커밋 author에 실명이나 개인 이메일이 없습니다. `git log --format='%an <%ae>' | sort -u`로 확인합니다.
- [ ] 저장소 이름과 소유 계정이 실명이나 개인 계정을 드러내는지 검토했습니다. 필요하면 팀 Organization으로 옮기거나 이름을 바꿉니다.
- [ ] 영상과 스크린샷에 계정, 알림, 개인 정보가 보이지 않습니다.
- [ ] API 키, 서명 키, Pleos My Project 자격 증명이 없습니다.
