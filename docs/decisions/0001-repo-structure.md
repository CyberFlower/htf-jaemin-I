# 0001. 저장소 구조와 문서 체계

- 상태: Accepted (초기 세팅, 2026-11-12). 이견이 있으면 PR로 제안합니다.
- 날짜: 2026-11-12

## 맥락

- 5명이 두 프로젝트(다녀왔습니다, 내 차로 짓는 도시)를 동시에 기획합니다. 세부 기획과 요구사항은 아직 정해지지 않았습니다.
- 팀원들은 Claude Code와 Codex를 함께 씁니다. 두 에이전트가 같은 규칙과 맥락을 읽어야 합니다.
- 1차 접수 마감은 2026-11-15입니다. 접수양식이 곧 기획서이므로, 요구사항 문서를 양식 원고로 옮기기 쉬워야 합니다.
- 두 프로젝트는 연결될 수 있습니다. game의 퀘스트가 grandma식 동행 여정을 받아들이는 안을 검토 중입니다.

## 결정

1. **단일 저장소**를 씁니다. `projects/grandma`, `projects/game`에 프로젝트별 문서를 두고, 공모전에 관한 사실은 `docs/contest` 한 곳에 모읍니다.
2. 프로젝트마다 **같은 문서 세트**를 둡니다: `README`, `GOAL`, `REQUIREMENTS`, `PROPOSAL`, `OPEN_QUESTIONS`, `DECISIONS`.
3. 에이전트 규칙은 **`AGENTS.md` 한 곳**에 씁니다. Codex는 이 파일을 기본으로 읽고, `CLAUDE.md`는 `@AGENTS.md`로 가져옵니다.
4. `draft/`는 v0.1 원본으로 보존하고 고치지 않습니다.
5. 요구사항은 **ID마다 절을 따로** 씁니다. 큰 표로 쓰면 동시에 고칠 때 충돌이 잦기 때문입니다. 목록은 grep으로 봅니다.
6. 목업 구현 방식이 정해지기 전에는([0002](0002-mockup-implementation.md)) 제품 코드 스캐폴딩을 만들지 않습니다. 실험은 `spikes/` 아래에서 합니다.

## 고려한 대안

- **프로젝트별 저장소:** 제출에는 깔끔하지만 공통 문서와 규칙이 중복되고, 두 프로젝트의 연계 논의가 흩어집니다. 출품 방식에 따라 제출용 저장소는 나중에 분리할 수 있습니다([open-questions.md](../open-questions.md) Q1, Q2).
- **`CLAUDE.md`와 `AGENTS.md`를 따로 작성:** 시간이 지나면 두 규칙이 서로 달라집니다.
- **Notion 같은 외부 문서 도구:** 에이전트가 직접 읽고 고치기 어렵고, git 이력으로 결정을 추적할 수 없습니다.

## 결과

- 좋은 점: 에이전트와 사람이 같은 맥락에서 일합니다. 결정과 변경 이유가 git 이력에 남습니다.
- 감수할 점: 두 앱을 한 저장소로 제출하면 README 필수 항목을 앱별로 나눠 써야 합니다.
- 후속 작업: 출품 방식이 정해지면(Q1) 제출용 README 구조를 확정합니다.
